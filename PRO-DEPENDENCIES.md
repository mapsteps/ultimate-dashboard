# What Ultimate Dashboard PRO relies on in free

PRO is an add-on: it only runs on top of the free plugin and builds directly on free's code. Everything below is an API, even if it looks internal. Changing it breaks PRO, often silently (no error, a feature just stops working).

Customers update free and PRO at different times, so the new free must keep working with the PRO version that's out there (3.11.4 at the start of the redo).

## Check

```
php bin/check-pro-deps.php
```

Checks the free code against the full list in `bin/pro-deps.json` (about 200 items). Run it after every change in free. It must say "All … OK". It reads the source, so it doesn't replace testing with PRO active.

## The rules

1. **Classes**: never rename or move a class, or change its namespace. PRO extends `Base_Module`, `Base_Output`, `Content_Helper` and `Widget_Helper`, and calls about 20 others by name.
2. **Methods**: never rename a public method PRO calls, or change its arguments. Adding optional arguments at the end is fine.
3. **Singletons**: PRO calls `get_instance()` on free classes. Every free class keeps `get_instance()` and registers its hooks on that same instance (not `new self()`), because otherwise PRO can't unhook them.
4. **Unhooked callbacks**: PRO removes 14 of free's callbacks by hook name, method name and priority (for example `login_head` → `print_login_styles` at 20). If any of the three changes, PRO stops removing the callback and both plugins' code runs. Keep all three exactly as they are.
5. **Hooks**: never rename or remove a `udb_` action/filter that PRO uses (84 of them), and never change what it passes or what it expects back. Some pass free objects (e.g. `udb_admin_page_setup_menu` passes free's admin page output, `udb_ajax_before_get_admin_menu` passes free's menu handler), so those objects' methods count too. Adding new hooks is fine.
6. **`*_field_path` filters**: PRO swaps whole field templates through them. The template file can change, but the field names inside (and so the saved option keys) must stay the same.
7. **Constants**: `ULTIMATE_DASHBOARD_PLUGIN_DIR`, `_URL`, `_VERSION` stay. PRO uses free's version number for some of its assets.
8. **Files**: PRO loads 10 free files by path (heatbox.css, admin menu/bar list templates, admin page edit template, login redirect URL field). Never move or rename them.
9. **Scripts & styles**: PRO's scripts load after free's by handle (`udb-dashboard`, `udb-edit-widget`, `udb-login-redirect`, `udb-login-customizer-preview`, `udb-branding-instant-preview` …). PRO swaps `udb-admin-menu` and `udb-admin-bar` for its own versions. Keep the handles. Changing the markup, CSS classes or JS in those screens can break PRO's add-ons on top, so test with PRO.
10. **Data**: options (`udb_settings`, `udb_branding`, `udb_login`, `udb_admin_menu`, `udb_admin_bar`, `udb_login_redirect`, `udb_modules`) and their inner keys, post types (`udb_widgets`, `udb_admin_page`) and their meta keys, admin page slugs (`udb_settings`, `udb_branding`, `udb_tools` …), AJAX actions and nonce names. Never rename them. PRO's license page sits under `udb_widgets`.

## Allowed in free

- Fixing bugs, escaping, sanitizing, capability checks, as long as everything above stays the same.
- New code, new files, new hooks.
- Restyling admin screens (heatbox), but test every screen with PRO active, since PRO adds fields and buttons there.
- Code that's only used by free can change freely. Check `pro-deps.json` first.

## Notes for the PRO pass

- Multisite branding removes PRO's own dark mode styles from `admin_head`, but they're registered on `admin_enqueue_scripts` (priority 100), so the removal does nothing.
- PRO hooks `udb_branding_login_styles`, which neither plugin fires.
- Multisite login redirect points at `modules/login-url` in free, which doesn't exist.
- Widget output checks `property_exists( $array_helper, 'clean_unserialize' )`, which is always false for a method (should be `method_exists`), so it never cleans double-serialized roles/users.
- Widget and admin page role/user fields call plain `unserialize()` (5 spots); use free's `clean_unserialize()`, which no longer unserializes objects.
- Admin pages are publicly queryable (page builders edit them on the frontend, block/Divi pages are shown in an iframe of the frontend URL). Free only keeps logged-out visitors out, so any logged-in user can open an inactive or role-restricted admin page on the frontend (`?post_type=udb_admin_page&p=ID`). A role check there has to work for multisite blueprint pages too.
- Branding output (`class-branding-output.php` ~line 345) reads `$branding['layout']` without `isset`: PHP warning when branding is enabled but no layout is saved (e.g. after an import).
- "Remove Data on Uninstall": free now deletes only on uninstall (`uninstall.php`), everything incl. widgets and admin pages. PRO still deletes its data on *deactivation*, and when free isn't loaded it also deletes `udb_settings` (it assumed that was the flag free restored). Move PRO's deletion to its own `uninstall.php` and stop deleting `udb_settings`; free keeps the flag for PRO when PRO is still active at free's uninstall.
- Login redirect per role: free now only redirects when no specific destination was requested (empty or the admin start page). PRO's multisite version (`class-ms-login-redirect-output.php`, which unhooks free's) should do the same.
- Admin menu editor, Users tab: free's `udb_admin_menu_get_users` sends every user on the site at once, and PRO's script puts them all in one dropdown. Slow on big sites. Make it a search-as-you-type field (select2 with an AJAX search, limited results); free's handler can take an optional search term without breaking the current call.
- Admin menu editor: PRO's `admin-menu.js` puts the user's display name into the tab HTML without escaping (`{display_name}`). Escape it like free now does (`wp.escapeHtml.escapeHTML`) and add `wp-escape-html` to the script's dependencies.
- Admin menu editor: free removed the never-working "recent menu" step (`save_recent_menu`, `udb_recent_admin_menu`). PRO never used it; the option is still deleted on uninstall for old installs.
- Tools: export & import now post to `admin-post.php` (`udb_tools_export` / `udb_tools_import`, nonce field `udb_tools_nonce`) instead of `options.php` + sanitize callbacks. Everything PRO hooks stays the same: `udb_export_fields` (inside the export form), `udb_export` filter (export modules still in `$_POST['udb_export_modules']`), `udb_import_settings` then `udb_import` with the decoded file, notices via `add_settings_error( 'udb_export', … )` (free carries them over the redirect like options.php). `Tool_Module::add_settings` stays on `admin_init` and now registers the handlers, so PRO's multisite unhook still switches the tools off on non-blueprint sites. New: `udb_import_settings` also fires when the file only has `multisite_settings` (free's "Settings imported" notice only shows when free settings were in the file). Older free never fires it for such a file, so PRO also imports network settings on `udb_import` when that didn't happen yet.
- Widget edit screen: free's widget types now use one box per type ("Icon Widget", "Text Widget", "HTML Widget") with the fields inside, each with a bold `.udb-field-label` above it, instead of one box per field. PRO's video and contact form widgets (`templates/widget-types/*.php`) still use one box per field; give them one box each the same way. Keep the `data-type` wrappers and field names.
- Widget and admin page lists, "User Roles" column: PRO's `roles_column_content()` (widget and admin page modules) returns the raw role keys joined with commas (`administrator, editor`), which free then runs through `ucwords()`. Return the translated role names instead (`translate_user_role( wp_roles()->role_names[ $key ] )`), and "All" for `all`.
- Login customizer, Log In button height: WordPress now gives buttons `min-height: 40px`, so heights below 40px did nothing and the old default (35px) was never used. Free now prints `min-height` with the height, targets only the Log In button (`.wp-core-ui .button.button-large`, like the live preview; it used to set height and padding on every `.button` on the login page) and defaults to 40px. PRO's own copy (`modules/login-customizer/inc/login.css.php`, `'35px'` fallback, `.wp-core-ui .button` block) needs the same change.
- Login customizer (3.9): `udb_login_styles_before_custom_css` filters free's login styles right before the custom CSS is added; PRO adds its left/right layout styles there (older free: PRO falls back to cutting the custom CSS off the end in `udb_login_styles`). Free now also prints the form's side padding (`form_horizontal_padding`) in the default layout, so PRO's `login-layout.css.php` no longer does.
- Tools, export checkboxes: PRO's `add_export_fields()` (tool module and multisite module) prints plain `<p><label><input class="udb-module-checkbox">` checkboxes. Free's tools script now moves them into its heatbox checkbox list and gives them heatbox's markup. Output heatbox's markup directly instead: `<div class="setting-field"><label class="label checkbox-label">Text<input type="checkbox" name="udb_export_modules[]" class="udb-module-checkbox" value="…" checked><div class="indicator"></div></label></div>` (the script leaves labels that already have `checkbox-label` alone). Also switch `_e( …, 'ultimatedashboard' )` to escaped output.
- Admin menu editor: same row change as the admin bar below (`menu-list.php`, `submenu-list.php`, `menu-separator.php`). The upsell banner is gone; free shows a PRO badge and an attached heatbox CTA strip instead, and only prints the footer (`udb_admin_menu_form_footer`) when PRO is active. Its Save also reloads without a message.
- Admin bar editor: free's row templates now use real buttons in the same spots (`button.hide-menu` for show/hide, `button.button.expand-menu` with the text "Edit" instead of the arrow). PRO's script still finds them by class and DOM depth, so nothing has to change, but PRO's add-item and submenu markup in `admin-bar.js` (if it builds rows itself) should match. After saving or resetting, PRO's script just reloads the page, so there's no "Settings saved" message; show one (e.g. reload with `&settings-updated=true` and print a notice).
- Admin bar/menu editor icon field: free's row templates now use the new icon picker (`icon-picker`, Dashicons only, value still saved as `dashicons-…`) with a hidden `input.udb-menu-builder--icon-field` that keeps its name and `data-name`; picking fires `change` on it, which PRO's scripts already listen to. PRO's scripts still call `.dashiconsPicker()` on `.dashicons-picker`, which now matches nothing, so free keeps loading the old `dashicons-picker` script (PRO's scripts list it as a dependency). Remove those calls and the dependency. When the icon is cleared ("Use default" / "Remove icon"), PRO's change handler draws `<i class="dashicons ">` (empty); free's uses the input's `data-default`; do the same.
- Page headers: free's screens now follow heatbox (`h1.title` in the header, `hr.wp-header-end` where notices go, logo `alt=""`). PRO's License page (`udb-license`) still has the old span title and empty hidden `h1`; switch it the same way.
- Admin menu editor, Users tab: the remove "x" on a picked user (free's `user-tab-menu.php`, which PRO loads) is now a `<button class="dashicons dashicons-no-alt delete-icon udb-menu-builder--remove-tab">` instead of an `<i>`, with no children, so PRO's `removeTab` (`this.parentNode`) and `switchTab` (`e.target.classList.contains("delete-icon")`) work unchanged. Not yet clicked through with PRO active in the browser.
- Font Awesome is gone (3.9): icon widgets & admin pages use Lucide icons (saved as the bare name, e.g. `rocket`) or Dashicons; old Font Awesome values are drawn as the closest Lucide icon by `Udb\Helpers\Icon_Helper`. The `udb_font_awesome` filter and the "Remove Font Awesome" setting are gone. `Setting_Output::remove_font_awesome()` stays as an empty method because PRO's multisite `MS_Setting_Output::remove_font_awesome()` calls it: remove PRO's hook, method and its multisite "Remove Font Awesome" field if it has one. Anything in PRO that prints an icon widget's or admin page's icon itself should use `( new Icon_Helper() )->html( $icon )`.
